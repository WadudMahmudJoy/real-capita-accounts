# Phase 2C: Voucher Implementation Plan

## Purpose

Phase 2C plans the voucher engine implementation chunks based on the Phase 2B requirement lock. This document splits the voucher implementation into safe, reviewable chunks so each step can be verified before the next begins.

This is a planning document only. It does not change schema, API, frontend, roles, seed data, or any runtime behavior.

## Prerequisite

Phase 2B voucher requirement lock is complete and accepted. The following docs define what Phase 2C must implement:

- `docs/requirements/phase-2b-voucher-requirement-lock.md`
- `docs/architecture/phase-2b-voucher-model-proposal.md`
- `docs/acceptance/phase-2b-acceptance-criteria.md`

Phase 2C must not add anything beyond what is locked in those documents.

## Confirmed Constraints

- Only `ACCOUNTANT` role exists. No additional roles.
- No reports, no dashboard analytics, no payroll, no parties/customers/vendors.
- No file uploads, no business seed data, no approval workflow.
- No reversal/correction in the first implementation (only DRAFT and POSTED).
- Reports are derived from posted VoucherLine records, not stored as separate tables.

## Open Questions Still Pending

Before Chunk 2C-1 begins, Real Capita should confirm or defer:

- Voucher numbering: per-type (PV-0001, RV-0001` or per-company-wide `V-0001`?
- Voucher types: six-type model (Debit, Credit, Journal, Contra, Payment, Receipt) or simplified four-type?
- Physical SI No: mandatory or optional? (Lock doc says optional but recommended.)
- File attachments: needed or deferred? (Lock doc says deferred unless confirmed.)
- Voucher type changeability in draft phase: allowed or locked at creation?

**Default position for implementation**: implement the full six-type model with per-type numbering, optional physical SI No, no file attachments, and voucher type changeable in draft. If Real Capita later confirms a simpler model, the unused types and sequences can be removed in a follow-up.

## Chunk 2C-2: Backend Draft Voucher API

### Objective

Implement NestJS voucher module with draft-only CRUD endpoints guarded by the ACCOUNTANT role. No posting endpoint yet.

Endpoints:
- `POST /vouchers` -- create a draft voucher with system-generated voucher number.
- `PATCH /vouchers/:id` -- update a draft voucher (header fields and lines).
- `GET /vouchers` -- list vouchers (filterable by type, status, date range, fiscal year, period).
- `GET /vouchers/:id` -- get voucher detail with all lines.
- `DELETE /vouchers/:id` -- soft-delete a draft voucher (set isDeleted=true, deletedAt=now). Only drafts can be soft-deleted.

### Files Likely to Change

- `apps/api/src/voucher/` -- new module directory: voucher.module.ts, voucher.controller.ts, voucher.service.ts, dto/ directory (create-voucher.dto.ts, update-voucher.dto.ts, query-voucher.dto.ts).
- `apps/api/src/common/` -- possible shared helpers for voucher number generation.
- `apps/api/src/app.module.ts` -- register VoucherModule.
- `apps/api/src/generated/prisma/` -- used through existing PrismaService.

### Business Logic

- **Voucher number generation**: On creation, atomically increment `VoucherNumberSequence.lastNumber` using a PostgreSQL transaction (UPDATE ... RETURNING). Assign the next number per company+fiscalYear+voucherType. Prefix formatting (e.g., PV-0001) computed in application code; stored voucherNumber is the formatted string.
- **Fiscal year and period derivation**: From the voucher date, look up the active FiscalYear and matching AccountingPeriod. Reject if period is LOCKED or CLOSED, or fiscal year is closed.
- **Line validation on create/update**: Each line must reference an active LedgerAccount. If requiresProject=true, projectId is mandatory. If requireCostCenter=true, costCenterId is mandatory. If both project and cost center are provided, cost center must belong to the project. If isCashBank=true, a cashBankAccountId should be provided.
- **Draft-only operations**: PATCH and DELETE only work on DRAFT vouchers. POSTED vouchers cannot be edited or deleted.
- **Audit events**: Record VOUCHER_CREATED, VOUCHER_EDITED, and soft-delete events in AuditEvent.

### Strict Out-of-Scope

- No POST /vouchers/:id/post endpoint (posting is Chunk 2C-3).
- No voucher reversal/correction logic.
- No report, no trial balance, no financial statements.
- No party/customer/vendor references in VoucherLine.
- No file upload or attachment handling.
- No additional roles beyond ACCOUNTANT.
- No batch voucher creation.

### Verification Commands

## Chunk 2C-3: Posting Validation Service

### Objective

Implement the voucher posting endpoint with full validation, immutability enforcement, and audit event recording.

Endpoint: `POST /vouchers/:id/post` -- post a DRAFT voucher. Transitions status to POSTED, records postedAt and postedByUserId, makes the voucher and lines immutable.

### Files Likely to Change

- `apps/api/src/voucher/voucher.service.ts` -- add postVoucher method.
- `apps/api/src/voucher/voucher.controller.ts` -- add POST /vouchers/:id/post endpoint.
- Possibly `apps/api/src/voucher/dto/post-voucher.dto.ts` if request body needed (likely empty body; action identified by URL).

### Validation Rules at Post Time

The posting service must re-validate all rules even if validated at creation:

1. Debit total equals credit total.
2. Fiscal year has isActive=true and isClosed=false.
3. Accounting period has status=OPEN.
4. All referenced LedgerAccounts have isActive=true.
5. If any line's LedgerAccount has requiresProject=true, that line must include projectId.
6. If any line's LedgerAccount has requiresCostCenter=true, that line must include costCenterId. If both projectId and costCenterId, cost center must belong to the project.
7. Cash/bank type validation: Payment requires at least one cash/bank credit line. Receipt requires at least one cash/bank debit line. Contra requires exactly two cash/bank lines (one debit, one credit). Journal, Debit, Credit have no mandatory cash/bank requirement.
8. Voucher number already assigned; does not change at posting.
9. Posted immutability: after successful posting, status changes to POSTED, postedAt and postedByUserId are set. Future PATCH and DELETE requests on this voucher must be rejected.
10. Audit event: record VOUCHER_POSTED in AuditEvent with userId, action, entityType="Voucher", entityId=voucher.id, metadata with voucherNumber, voucherType, total amounts.

### Strict Out-of-Scope

- No reversal/correction endpoint.
- No unpost action.
- No balance table or stored ledger report.
- No report, no trial balance, no financial statements.
- No party/customer/vendor references.
- No file uploads.

### Verification Commands

```powershell
pnpm prisma:generate
pnpm typecheck
pnpm lint
pnpm build:api
pnpm build:web
pnpm check:all
pnpm doctor
```

### Manual Smoke Tests

- Create a draft voucher. Attempt to post with mismatched totals; verify rejection.
- Post a valid voucher. Verify status is POSTED, postedAt has timestamp, postedByUserId is set.
- Attempt PATCH on posted voucher; verify rejection.
- Attempt DELETE on posted voucher; verify rejection.
- Lock an accounting period, then attempt to post a draft voucher in that period; verify rejection.
- Verify AuditEvent records VOUCHER_POSTED.

### Recommended Model

GPT-5.5 Thinking xhigh / Codex for posting logic review and validation precision.

### Fallback Model

DeepSeek V4 Pro Max with strict prompt referencing Phase 2B posting rules.

### Risk Level

High. Posting is the core accounting integrity gate. If validation is wrong or skipped, posted vouchers will corrupt future report data. Must be reviewed carefully.

### Stop Condition

Stop if:
- Posting succeeds when debit total does not equal credit total.
- Posting succeeds when accounting period is LOCKED or CLOSED.
- Posting succeeds when fiscal year is closed.
- Posting succeeds when LedgerAccount is inactive.
- Posting succeeds when requireProject/requiresCostCenter flags are not satisfied.
- A posted voucher can be edited or deleted after posting.
- AuditEvent does not record VOUCHER_POSTED.
- `pnpm typecheck` or `pnpm lint` fails.
