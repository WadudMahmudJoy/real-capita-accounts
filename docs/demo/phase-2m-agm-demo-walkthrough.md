# Phase 2M AGM Demo Walkthrough

## Purpose

This runbook supports an AGM-ready walkthrough of the Phase 2M internal Customer Booking UI. It demonstrates customer setup, bookable item setup, booking control, receipt voucher allocation, and the accounting boundary between booking screens and voucher posting.

## Pre-Demo Reset And Checks

Run from the repository root:

```powershell
git status --short --branch
git log --oneline --decorate --max-count=5
pnpm demo:audit
pnpm demo:verify
```

If the demo database must be restored before the walkthrough:

```powershell
$env:CONFIRM_DEMO_RESET='YES'; pnpm demo:reset
pnpm demo:audit
pnpm demo:verify
```

Start the application stack using the project's normal local development command, then open the web app in the browser.

## Login Route

- Route: `/login`
- Use the existing internal accountant demo credential agreed for local demos.
- After login, the authenticated landing route is `/app`.

## Demonstration Flow

1. Login at `/login` and confirm the authenticated `/app` shell loads.
2. Open the `Customers & Bookings` navigation area and explain that these are internal accounting control screens.
3. Create a customer from `/app/customers/new`; point out that customer code is backend-generated and phone is required but not globally unique.
4. Create a bookable item from `/app/bookable-items/new`; explain that the item is project-linked and `BOOKED` is reached through booking creation.
5. Create a booking from `/app/bookings/new`; add at least one installment row with due date and BDT amount.
6. Open the booking summary page and show administrative status, derived financial status, net booking value, posted collected amount, pending allocation amount, total due, and next installment date.
7. Create a `RECEIPT` voucher through the existing voucher workflow at `/app/vouchers/new`; keep voucher creation and posting inside the voucher workflow.
8. Return to the booking detail page and allocate the existing `RECEIPT` voucher in the `Receipt allocation panel`.
9. Post the voucher through the existing voucher workflow; do not post from the booking screen.
10. Return to the booking detail page and show `Posted receipt collection` reflected in posted collected amount and due values.
11. Explain accounting controls: DRAFT allocation is pending only, POSTED receipt collection counts, and voucher posting remains accountant-controlled.

## Talking Points For AGM Sir

- The UI separates customer booking operations from voucher posting controls.
- Customer, item, and booking numbers are generated by the backend for audit-safe references.
- BDT amounts and dates use one display convention across the Phase 2M screens.
- Pending allocation means a draft voucher is linked but not counted as collection.
- Posted receipt collection means the linked receipt voucher has been posted and now supports the booking collection total.
- The booking screen provides a control/subledger view; the posted voucher remains the accounting evidence.

## Known Boundaries

- No client portal yet; all screens are internal authenticated `/app` screens.
- No reports are delivered in this phase.
- Voucher posting remains accounting-controlled in the existing voucher workflow.
- Receipt allocation links booking collection to voucher evidence.
- No PDF/Excel export, SMS, payment gateway, dashboard analytics, or public workflow is included.
- No Project Fund Movement behavior is changed by this phase.
